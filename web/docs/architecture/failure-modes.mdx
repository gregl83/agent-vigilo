## Worker crash

Chunk messages are delivered at least once. A worker holds the RabbitMQ delivery unacked while it owns the chunk lease. If the worker exits before acknowledgement, RabbitMQ redelivers the message and the next worker must win the database chunk claim before doing work.

## Duplicate delivery

Duplicate broker deliveries are allowed. Exactly-once effects are managed in the database: chunks can only be claimed from an open or expired lease, executions only accept terminal transitions from the current attempt id and attempt number, and evaluator results are unique per run, attempt, and evaluator.

## Outbox publisher crash

Outbox claims assign a `claim_token` and future availability window. A publisher only marks or reschedules an event while that token is still current. If it crashes, the event becomes available again and another coordinator can retry publication.

## Broker routing failure

RabbitMQ publishes use durable topology, persistent messages, mandatory routing, and publisher confirms. Unroutable or negatively acknowledged publishes leave the outbox row pending for retry instead of marking it published.

## Partial persistence

Worker persistence batches are guarded by current-attempt authority checks. If a stale worker loses authority, its final state changes are rejected rather than overwriting a newer attempt.
