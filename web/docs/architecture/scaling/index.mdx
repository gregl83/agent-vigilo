# Scaling

Agent Vigilo is designed to start with one PostgreSQL database and grow without changing application code. The default setup stores control data and execution data in the same database. The schema still records a stable `run_shard` for high-volume execution rows so those rows can later move to additional PostgreSQL placements.

## Default Setup

Most teams only need one database to start:

```text
DATABASE_URL=postgres://...
```

`vigilo setup` applies migrations, seeds the default placement catalog, and validates that the process can connect to the control database. These optional settings default to `primary`:

```text
VIGILO_CONTROL_DATABASE_ALIAS=primary
VIGILO_DEFAULT_SHARD_DATABASE_ALIAS=primary
```

The seeded catalog row is:

```text
alias = primary
database_url_env = DATABASE_URL
role = control_and_shard
status = active
```

That means all data routes to the same PostgreSQL database until you add another placement.

## Database Architecture

Agent Vigilo separates database purpose from database location:

- **Control storage** is the source of truth for evaluator registry rows, global run metadata, placement catalog rows, coordinator state, and other control-plane records.
- **Execution storage** holds high-volume run work: chunks, executions, attempts, aggregates, evaluator results, and shard-local workflow state.
- A **database placement** is a named PostgreSQL target such as `primary` or `shard_001`.
- A **shard placement** maps one `run_id + run_shard` pair to a database placement.

In the default deployment, `primary` has role `control_and_shard`, so it is both the control database and the execution database.

In a larger deployment, there is still only one active control-capable placement. Additional placements can have role `shard` and hold execution-owned rows. Routing changes by updating placement rows, not by changing worker or coordinator code.

Environment variables only hold connection secrets. The database placement catalog is the authority for which placements exist and what role each placement has.

## Current Implementation Status

Implemented today:

- 128 logical `run_shard` values.
- Shard-partitioned high-volume execution tables inside one PostgreSQL database.
- Placement catalog tables: `database_placements` and `shard_placements`.
- A seeded `primary -> DATABASE_URL` placement with role `control_and_shard`.
- Runtime configuration for the control alias and default shard-capable alias.
- Placement catalog validation during `vigilo setup`.
- Run creation inserts one active `shard_placements` row for each `run_shard`
  used by the run.
- A database service/router that exposes `control()` and execution routing primitives to DB/workflow code.
- Chunk-ready messages that carry `run_id`, `run_shard`, and `chunk_id`.
- Worker chunk-local processing resolves the execution database by
  `run_id + run_shard`; run profile and evaluator registry metadata remain
  control-plane reads. `moving` or `draining` shard placements delay worker
  messages instead of allowing new chunk claims.
- Coordinator dispatch selects dispatchable `run_id + run_shard` routes from
  control storage, resolves the execution placement, and runs a
  route-constrained shard dispatch statement. The dispatch statement prepares
  an execution-local run snapshot before inserting worker-visible chunk events.
- Chunk lease recovery runs bounded recovery passes per active execution
  placement.
- Durable outbox publishing runs once per active database placement. Control
  workflows publish from the control outbox; execution workflows publish from
  the execution placement that owns the changed rows.
- Worker chunk-local SQL uses the execution-local run snapshot instead of
  joining the authoritative control `runs` row.
- Shard-local `run_shard_summaries` roll execution/chunk progress up to one row
  per `run_id + run_shard`.
- Coordinator finalization reads those routed shard summaries, aggregates them
  in memory, writes the global `runs` outcome in control storage, and emits
  `run.completed` from the control outbox.
- `run results` reads global run metadata from control storage and combines
  routed shard summaries from execution placements.
- `run export --format jsonl` streams one routed run shard at a time and marks
  execution-scoped records with `run_shard` and `database_alias`.
- `run export --format json` pages routed shards and materializes a single JSON
  document for smaller exports.
- Result/export read routing can inspect `moving` or `draining` shard
  placements; those states block new work, not reads from the current source
  placement.
- `vigilo shard move` copies one `run_id + run_shard` to another execution
  placement, verifies row counts and checksums, and switches the routing row
  after verification.

Not implemented yet:

- Multi-placement assignment policy at run creation.
- Cancellation, status fanout, evaluator metadata replication, and canonical
  case-data routing/replication paths migrated to execution placement routing.

The current system should be read as **single-database operation by default,
with routed execution workflows being introduced behind the database service
boundary**.

## Current Shard Model

The system uses 128 logical shards:

```text
run_shard = 0..127
```

Run chunks receive a shard during run creation. Every execution, attempt, aggregate, and evaluator result produced from that chunk carries the same shard key:

```text
run_chunks(run_id, run_shard, id)
run_shard_dispatch_cursors(run_id, run_shard)
executions(run_id, run_shard, id)
execution_attempts(run_id, run_shard, id)
execution_aggregates(run_id, run_shard, execution_id)
evaluator_results(run_id, run_shard, id)
```

The high-volume tables are list partitioned by `run_shard`. A worker that owns one chunk can query by `run_id + run_shard + chunk_id`, keeping the chunk-local workflow on one partition per table.

## Default Single-Database Deployment

The default deployment can keep every logical shard on one PostgreSQL cluster:

```text
run_shard 0..127 -> primary PostgreSQL
```

No multi-cluster routing is required to start. The shard key still matters because it prevents one massive run from concentrating all execution writes into one physical partition.

## Queue and Worker Routing

Chunk-ready messages include the routing key:

```json
{
  "run_id": "00000000-0000-0000-0000-000000000000",
  "run_shard": 42,
  "chunk_id": "00000000-0000-0000-0000-000000000000"
}
```

Workers use `run_id + run_shard + chunk_id` to claim the chunk. In the default deployment every shard points at the same pool. Later routing phases will resolve `run_id + run_shard` to the correct execution placement before worker transactions start.

## Coordinator Dispatch Routing

Run creation stores one `run_shard_dispatch_cursors` row for every logical shard used by the run. Each coordinator dispatch window claims one open cursor with `FOR UPDATE SKIP LOCKED`, selects pending chunks only for that `run_id + run_shard`, and then either releases the cursor for another window or marks it drained when no undispatched pending chunks remain. Dispatch updates the parent `runs` row only when starting a pending run; already-running runs dispatch by cursor while taking only a compatible shared run-row lock.

This means a single dispatch statement is shard-local. A large run is not forced onto one shard; its chunks remain spread across the 128 logical shard range. Because open cursors are ordered by cursor update time, repeated dispatch windows rotate across a run's active shards instead of draining the lowest shard first. Multiple coordinators can claim different open shard cursors for the same already-running run without taking incompatible run-row locks, while cancellation and finalization still serialize through their exclusive lifecycle updates.

## Placement Reference

Placement metadata exists even in the default single-database deployment.

`database_placements` is the placement catalog:

```text
alias              stable placement name, such as primary or shard_001
database_url_env   environment variable that holds the connection URL
role               control, shard, or control_and_shard
status             active or disabled
```

`shard_placements` is the execution routing map:

```text
run_id + run_shard -> database_alias
```

The runtime router reads placement rows from control storage. DB workflow code can resolve execution-owned storage by `run_id + run_shard`, validate that the target alias is active and shard-capable, and return the pool for that placement.

Every new run must create placement rows for the `run_shard` values it uses. Missing `shard_placements` rows are setup or run-creation errors. Expansion changes placement rows, not the `run_shard` value stored on execution rows.

## Routing Boundary

The router is an infrastructure primitive, not an application-level decision
that should appear throughout thin command dispatch or generic runtime code.
Callers should express domain intent through workflow functions such as
evaluator publishing, run creation, chunk processing, dispatch, finalization,
and export. Those workflows decide whether their data lives in control storage,
execution storage, or both.

Inside those DB/workflow boundaries, control storage is accessed through the
database service's control pool and execution-owned storage is resolved by
`run_id + run_shard`. Outside those boundaries, code should not care whether a
run uses one database placement or many.

This keeps topology decisions contained:

- Evaluator registry workflows use control storage internally.
- Run metadata workflows use control storage internally.
- Chunk and execution workflows route execution-owned data by `run_id +
  run_shard` internally.
- Run finalization fans out across execution placements for shard summaries and
  writes the global run outcome to control storage.
- Run-level reporting and export workflows fan out across execution placements
  internally.
- Thin command dispatch and generic runtime code should not choose between
  control and execution databases directly.

## Adding An Execution Database

The `database_placements` table is the authoritative placement catalog. Environment variables provide secret connection values and process-local defaults; they must not duplicate the placement catalog.

When adding a shard placement, deploy the matching secret env var and add the
database placement:

```text
VIGILO_SHARD_001_DATABASE_URL=postgres://...
vigilo shard databases add shard_001 --database-url-env VIGILO_SHARD_001_DATABASE_URL
```

The command creates an active shard-only placement. It validates that the env
var is present unless `--defer-env-validation` is passed deliberately.

After that, new `shard_placements` rows can point selected execution shards at
`shard_001`:

```text
vigilo shard placements set <run_id> <run_shard> --alias shard_001
```

This is only allowed for an empty or new `run_id + run_shard`. If the current
active placement already has shard-owned rows, use the shard move workflow
instead of directly changing the alias.

The initial assignment rule is deliberately simple: every new run shard maps to
`VIGILO_DEFAULT_SHARD_DATABASE_ALIAS` when placement rows are created. Richer
policies should be introduced only with an explicit admin/config contract,
because routing must read stored `shard_placements` rows instead of
recalculating from current placement count.

Useful inspection commands:

```text
vigilo shard databases list
vigilo shard placements list <run_id>
vigilo shard placements show <run_id> <run_shard>
```

## Migration Runbook

Use this procedure when moving logical shards to a new PostgreSQL placement.

1. **Choose shard scope.** Select one `run_id + run_shard` pair.
2. **Preview the move.** Run:

```text
vigilo shard move <run_id> <run_shard> --alias <alias> --dry-run
```

3. **Move after work drains.** Run the move once selected chunks are no longer
   `leased` and attempts are no longer `running`:

```text
vigilo shard move <run_id> <run_shard> --alias <alias>
```

The normal command marks the shard placement `moving`, copies rows, verifies
counts and checksums, then switches the placement to the target alias with
status `active`. `--dry-run` and `--verify-only` are read-only. Use `--force`
only for an explicit unsafe copy while active work remains.

4. **Copy shard-owned rows.** The move workflow copies rows for the selected
   shard scope from the source placement to the target placement:

```text
run_chunks
run_snapshots
executions
execution_attempts
execution_aggregates
evaluator_results
run_shard_summaries
```

It also copies the required `dataset_versions` and `runs` rows to satisfy local
foreign keys on the target placement. `run_shard_dispatch_cursors` remains
control-plane metadata and is not copied between execution placements.

5. **Verify data.** To compare an already-copied source and target without
   copying or switching placement, run:

```text
vigilo shard move <run_id> <run_shard> --alias <alias> --verify-only
```

6. **Switch placement.** The successful move command updates the placement row
to `active` on the new `database_alias`.
7. **Resume dispatch.** Coordinators and workers resolve the same `run_id + run_shard` to the new database placement and continue processing.
8. **Retain then clean up.** Keep source rows read-only for a retention window. Source cleanup is outside the move command and should happen only after verification and backup policy allow it.

## Migration Standards

- `run_shard` is stable for the lifetime of a chunk and its child rows.
- Do not recalculate `run_shard` when adding database capacity.
- Queue messages must include `run_shard`; workers should not rediscover it with an extra lookup on the hot path.
- Coordinator dispatch should claim `run_shard_dispatch_cursors` and select chunks by `run_id + run_shard`, not scan all chunks for a run.
- Chunk-local worker queries should include `run_id` and `run_shard`.
- Joins between shard-partitioned run tables must use the full logical key, including `run_shard` (for example `run_id + run_shard + execution_id`), so result queries preserve partition locality and cannot cross-match rows from different shards.
- Run-level reporting may fan out across all 128 shards for the run.
- Large payload artifacts should be moved outside PostgreSQL before cross-cluster movement becomes routine.

## Recreating a Database

For a fresh deployment, apply the original migration files normally. The 128-shard schema is part of the create-table migrations.
